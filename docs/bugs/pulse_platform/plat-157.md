# PLAT-157 — `call_sub_agent` makes parents repeat child contracts and uses a non-unique todo label to inspect executions

| Coordination | Value |
|---|---|
| Assigned agent | Codex |
| Ticket state | `implemented` — focused tests pass; live workflow reverify pending |
| Last synchronized | `2026-08-19` |

- **Priority:** P1 — the contract encourages large duplicate handoffs and can
  inspect the wrong retry when one todo is delegated more than once.
- **Owner:** workflow todo-task sub-agent tools and orchestrator guidance.

## Evidence and RCA

The parent prompt claimed that predefined children could not see their schema,
learnings, objective context, or route instructions, and therefore told the
parent to copy all relevant context into every `instructions` argument. That is
not the runtime contract. A predefined route receives its saved description,
validation schema, declared file dependencies, skills, store permissions, and
route learnings when its child agent is constructed. Recopying those facts
wastes context and encourages broad `rg`/file dumps before delegation.

A live Social Media execution on 2026-08-19 captured the resulting behavior.
Before calling route `execute-trending-radar`, the parent ran `rg` across the
global learning references, fetched `get_route_description` despite already
having selected the route, and then repeated output keys, the upstream artifact
path, learning state, and browser-sharing choice inside `instructions`. During
that continuing turn, individual shell receipts returned roughly 25–52 KB and
one later shell invocation carried about 47 KB of arguments. This is evidence
of the bad handoff contract in use, not a reason to impose a mechanical output
size limit on the agent.

The runtime compounded this on stateful message-sequence routes. It combined
the standing route description with the dynamic instruction for the first call,
then replayed that combined text as the user message on every later call. The
same standing contract therefore accumulated repeatedly in one conversation.

Diagnostics had a separate identity defect. `call_sub_agent` returns a unique
`execution_id`, and `query_sub_agent`/`stop_sub_agent` correctly use it, but
`get_sub_agent_conversation` accepted `todo_id`. A todo may have multiple
attempts, routes, or concurrent executions, so the lookup selected the newest
matching label rather than the exact execution the parent intended to inspect.

## Identifier boundary

- `route_id` is a valid parent-side selector for a configured specialist. It is
  resolved by the runtime and is not meaningful task context handed to the
  child.
- `todo_id` links delegated work to the orchestrator's durable todo item and
  artifact naming. It is a task-management identity, not a child instruction.
- `execution_id` is generated by the runtime for one exact invocation. It is
  the only identity used for query, stop, and conversation diagnostics.

This separation keeps semantic choices agentic while making lifecycle identity
deterministic.

## Fix and reasoning

1. Predefined-route guidance now tells the parent to pass only current-run facts
   absent from the saved route contract. Generic agents still require a
   self-contained brief because they have no standing route.
2. `get_route_description` is optional when the short route catalogue already
   makes the choice clear; it is no longer prescribed before every delegation.
3. Stateful route continuation sends only the new dynamic instruction. The
   durable description remains opening context and is not replayed.
4. `get_sub_agent_conversation` now requires the exact returned
   `execution_id`; call-history records retain that ID.
5. The obsolete `share_browser` choice was removed. Browser-capable children
   inherit the workflow browser session; the parent serializes conflicting
   browser work when necessary.

## Related boundaries

- PLAT-156 removes Go-authored semantic plan interpretation and full-plan prompt
  injection from `review_plan`.
- PLAT-151 removes the dead `context_to_pass` field; descriptions, declared
  dependencies, managed stores, and dynamic instructions are the real channels.
- PLAT-138 lets a new Engineering review selectively reuse the latest relevant

## Acceptance

1. A repeated message-sequence route receives only the latest dynamic
   instruction as its continuation turn.
2. The first route call still receives its saved description plus the initial
   dynamic request.
3. Parent guidance does not ask it to copy a predefined child's saved schema,
   learnings, route description, or broad logs into `instructions`.
4. Route details are fetched only when the short catalogue is insufficient.
5. Query, stop, and conversation inspection all use `execution_id`.
6. Two executions for one todo can be inspected independently.
7. No `share_browser` parameter or isolated-browser context remains in the
   workflow sub-agent contract.
