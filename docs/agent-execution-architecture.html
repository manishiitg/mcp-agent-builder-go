How the agent actually executes

Docker · the MCP bridge · the terminal (tmux) agent — and where the security boundaries really sit. Written against the code as of 2026-07-27. Everything below was verified by reading the source or running it; where something is untested it says so explicitly.

The key idea: there are two separate execution paths, with different sandboxes and different threat profiles — plus a third actor, the parent's own Chrome, that no sandbox here can reach. Most confusion about "is the agent isolated?" comes from not knowing which path a given call took.

host process — trusted, unsandboxed

1The terminal agent (tmux)

Coding CLIs are interactive TUIs, so they are driven inside a tmux pane: the server writes keystrokes with tmux send-keys and reads the screen with capture-pane.

Why any sandbox must go inside the pane

tmux is client/server. Wrapping the tmux command would sandbox the client, while the pane is created by the already-running tmux server — a different, unsandboxed process. The wrapper is therefore built into the pane's command string:

sandbox-exec -f /tmp/agentworks-codex-sandbox-XXXX.sb   ← kernel FS policy
  /bin/sh -c '/usr/bin/env -i                            ← wiped environment
       PATH=… TERM=… HOME=/Users/you CODEX_HOME=…/.codex
       /opt/homebrew/bin/codex <args>'

sandbox-exec is a real boundary

macOS Seatbelt — kernel-level mandatory access control, enforced per syscall and inherited by every descendant. Verified: a shell, its bash -c child and a python3 grandchild were all equally blocked.

Currently unused for the CLI in SparkQuill The CLI itself runs in Compatibility mode — no sandbox wrapper at all. That matters less than it sounds, because bridge-only mode removes its ability to act (below).

2The MCP bridge — the real chokepoint

The model's tools are Go functions in the server process. The bridge is how it reaches them:

model calls a tool
  → CLI invokes its MCP server        (--mcp-config)
  → mcpbridge (stdio subprocess)      MCP_TOOLS / MCP_API_URL / MCP_API_TOKEN
  → HTTP POST /tools/custom/{name}    bearer token + X-Session-ID
  → executor server                   same process as the agent
  → Go handler runs

Each CLI's own native tools are switched off so the bridge is the only way to act — Codex --disable shell_tool, Cursor a deny-list, Claude an --allowed-tools allowlist, Pi --no-builtin-tools.

Verified: native file access really is gone Asked to read a file using only its built-in ability, the CLI returned NATIVE_READ_BLOCKED. The control matters more: asked to read a file inside the workspace the same way, it returned NO_NATIVE_TOOL — so the tool is genuinely absent, not the model being agreeable. Tested on codex-cli only; the other three use different flags.

Bridge tools are sandboxed separately

execute_shell_command does not inherit the CLI's sandbox — it runs in the trusted server process, wrapped in its own isolator (workspace/security.Isolator: sandbox-exec on macOS, unshare on Linux). Two paths, two sandboxes. No Docker is involved in shell execution.

3What was leaking, and what changed

The isolator has two profiles. The default denies only the app's own project root and allows the rest of the host — deliberate, so AgentWorks workflows can drive user-installed CLIs (aws, gcloud, kubectl). StrictAllowlist flips it to genuine deny-by-default. The child's shell always used strict; the parent's did not.

Measured with a decoy file (before) The parent's execute_shell_command returned the full contents of a file in the real home directory. Exactly what RFC #181 predicted: "a workflow shell can read unrelated home files."

SparkQuill needs none of those developer CLIs — and its last host-CLI dependency (gws) was removed the same day — so the tradeoff justifying the permissive default does not apply. The parent shell now sets StrictAllowlist: true.

Why node still runs node is nvm-installed under $HOME, which is now denied — yet it works, because Seatbelt treats process-exec separately from file-read-data. A home-installed interpreter still executes; it just cannot read home data.
This is the one isolation that holds for every provider It runs in the server process, not the CLI, so switching engine in Settings cannot weaken it — unlike clisandbox, which only implements Codex.

4The browser bypass

Closing the shell path exposed a second one. agent_browser drives the parent's own CDP Chrome — a pre-existing host process this app does not own. It reads with the user's full privileges, so no sandbox applied to our child processes can reach it.

Measured (before) 
shell:   cat ~/decoy.txt          → Operation not permitted   ✅
browser: file:///Users/…/decoy.txt → SPARKQUILL_BROWSER_BYPASS_9X4Q   🔴
The browser read a file the shell had just been denied. This predated the strict-mode change — closing the shell door only made it visible.

Fixed with a scoped allowlist in browser_tool.go (not a blanket block — previewing a generated page or a downloaded PDF is legitimate): file:// URLs must resolve inside the workspace or Downloads. Validation runs after secret substitution, so what is checked is exactly what reaches the browser. Denied spellings, all unit-tested:

spellingresult
file:///etc/passwd · ~/.ssh/id_rsadenied
FILE://… (case) · view-source:file://…denied
../ traversal · %2e%2e URL-encoded traversaldenied
symlink inside workspace pointing outdenied
file://evil.example.com/sharedenied
file:// inside the workspacestill allowed
Severity was read-only Writes go through FinalizeBrowserArtifact / StageBrowserUpload, which validate destinations against the write paths. But read alone is enough to exfiltrate — once a credential is in the model's context it can be put in a reply or a workspace file. Untested: CDP's Browser.setDownloadBehavior could redirect downloads to an arbitrary directory; whether agent-browser exposes it has not been checked.

5Docker

Namespaces + cgroups: the container has its own root filesystem and sees the host only through bind mounts (./workspace-docs, ./agent_go/configs, ./agent_go/logs). Stronger than sandbox-exec in principle, and no macOS Keychain to worry about. Two things undercut it:

a. The coding CLIs are not in the image Grepping agent_go/Dockerfile for claude-code|@anthropic|codex|cursor-agent returns 0 matches — only agent-browser, plus pi-cli behind a build arg. Docker isolates the agent server, not the CLIs, which still run on the host terminal. And family-server (SparkQuill) is in neither compose file.
b. The Docker socket is mounted in /var/run/docker.sock is bind-mounted into agent-server with docker-ce-cli installed (deliberately — prod labels it "DooD: manage sibling project containers"). Anything inside can ask the host daemon to start a container mounting /, giving root on the host. Namespace isolation is real; this routes around it.

6Security modes — where they stand

Verified fits the usual goal; Isolated usually does not. The threat is a CLI reading your keys and files — not a CLI using your own subscription. So ~/.codex/auth.json is not a problem to solve, it is the one thing you deliberately grant back via HostReadPaths. Isolated (private $HOME + a fresh login) buys account separation and charges a per-provider login for it.

blockerdetail
Only Codex is enforced Only clisandbox.PrepareCodexCommand exists. The other three call ValidateCLISecurityLaunch with zero enforced modes — a strict mode fails closed (safe) but breaks the product. With the engine user-switchable in Settings, covering 1 of 4 is not a boundary. Does not affect §3/§4, which live in the server process.
Claude Code's keychain Its session is keychain-only. Denying home also denies ~/Library/Keychains/login.keychain-db, so the lookup fails — measured: security find-generic-password succeeds unsandboxed, "not found" sandboxed. So it cannot authenticate at all, and granting it back is all-or-nothing, since that file holds every other secret the user owns. Unlike ~/.codex/auth.json, which is scoped and safe to grant.
Network is unrestricted Both profiles constrain the filesystem only. A prompt-injected command cannot read your keys but can still make arbitrary outbound calls.
